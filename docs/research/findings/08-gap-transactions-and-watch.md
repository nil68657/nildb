# NilDB transaction and concurrency model: Kvrocks WATCH/EXEC on RocksDB, Redis 6.0.9+ WATCH-over-expiry semantics, RocksDB WriteBatch vs OptimisticTransactionDB vs TransactionDB, and Dragonfly's VLL design as the third data point

Exported on 2026-09-27 from the NilDB deep-research workflow (Claude Code run `wf_1b4f4c38-bbf`, step `gap:3`, agent `a40dd9c4533cd6fb6`, researched 2026-09-26). The text is the agent's structured output, unedited; confidence labels are the agent's own.

## Design implications

1. Pick one coherent EXEC model and write it down once. The evidence favours: open a plain rocksdb::DB (not TransactionDB), keep NilDB's own striped per-key lock manager (Kvrocks already has one for single commands), and run EXEC as: sort and lock every key named in the queued commands, verify WATCH state, execute the queue into one WriteBatchWithIndex with GetFromBatchAndDB/NewIteratorWithBase for read-your-writes, db->Write once, unlock. This gives Redis's serial-isolation guarantee for the keys involved without stopping other workers and without any RocksDB transaction layer. Commands whose key set is unknown until execution (SCAN-driven scripts, KEYS) are the exception and need either a global mode (as Dragonfly does) or a rule that they are refused inside MULTI.
2. Do not adopt Kvrocks's global std::shared_mutex around all command execution. The HTAP promise depends on analytical commands not sharing a lock with EXEC. On macOS the libc++ writer-preferring shared_mutex turns 'EXEC waits for a 5-second aggregation' into 'every client on every worker stalls for 5 seconds'. If any process-wide guard is kept (for FLUSHALL, SHUTDOWN, config reload), analytical scans must take their RocksDB snapshot and then release the guard before iterating, and the scan must be cancellable.
3. If RocksDB-level conflict detection is wanted anyway, OptimisticTransactionDB is the only one of the two that does not tax every non-transactional Put/Delete with lock acquisition; TransactionDB locks all keys of every DB::Write unless skip_concurrency_control is set globally (which defeats the point) or per write. But OptimisticTransactionDB brings: Busy and TryAgain at commit that the Redis protocol has no way to express except as a nil EXEC reply and a client retry; a dependency on max_write_buffer_size_to_maintain being large enough to cover the WATCH..EXEC window; and no DeleteRange, which rules out the cheapest FLUSHDB/namespace-drop implementation. That combination is why Kvrocks and Dragonfly both chose server-side locking over RocksDB transactions.
4. Implement WATCH to the Redis 6.2.5+ contract that multi.tcl exercises: (1) at WATCH time, record per key whether it is already logically expired (a metadata point read); (2) at EXEC, before executing, re-read the TTL of every watched key not flagged at WATCH time and abort with nil if any is now expired (Redis isWatchedKeyExpired, Dragonfly's EXISTS hop); (3) mark watched keys dirty only from write commands' declared key ranges, and only after the command succeeded; (4) FLUSHDB/FLUSHALL/SWAPDB must dirty only keys that currently exist and must clear (not trip) the flag for keys that were already stale, otherwise 'FLUSHALL does not touch non affected keys' and 'FLUSHDB while watching stale keys should not fail EXEC' fail. Kvrocks's mark-every-watcher shortcut fails these.
5. Because NilDB, like Kvrocks, will expire lazily via compaction filters, there is no deletion event to hook. WATCH-over-expiry therefore has to be pull-based at EXEC (finding above), and the same applies to keyspace 'expired' notifications and to any secondary index (geo) maintenance: plan for readers to tolerate stale index entries whose primary metadata reports Expired().
6. Key the watched-key table by (namespace or db index, key), not by raw key. Kvrocks stores raw user keys, so a write to key 'x' in one namespace dirties a WATCH on 'x' in another. Also keep the two-level structure (key -> set of connections, connection -> set of keys, connection dirty flag) so the hot path on writes is one hash lookup guarded by a shared lock, and skip it entirely when no key is watched (Kvrocks's atomic size counter).
7. Keep the WATCH check and the commit inside the same critical section for the keys involved: Kvrocks does this trivially because EXEC is globally exclusive; with per-key locking NilDB must acquire the queued commands' key locks first, then test the dirty flag, then run and commit, otherwise a write between the check and the commit slips through.
8. Snapshot isolation for analytics is free at the RocksDB layer: a rocksdb::Snapshot pins a sequence number and blocks nothing; what blocks is only whatever server lock the scan holds. Design analytical commands to hold no server lock while iterating, to pin their own snapshot, and to release it promptly; long-lived snapshots delay compaction garbage collection but never block EXEC or writers.
9. Run the measurement before committing: db_bench --benchmarks=randomtransaction on the target Apple Silicon box with (a) no txn flag (WriteBatch), (b) --optimistic_transaction_db=1, (c) --transaction_db=1, at --threads 1,4,8,16 and --transaction_sets 1 and 4, with --allow_concurrent_memtable_write=1 --enable_write_thread_adaptive_yield=1, and report the abort counts. Callaghan's 2016 numbers (pessimistic costs 3-28% over WriteBatch, worst single-threaded) are the only public reference and lack the optimistic column and Apple Silicon.
10. Errors inside EXEC must not roll back: both Redis (docs) and Kvrocks (comment in CommandExec) commit the remaining commands and return per-command errors. A WriteBatchWithIndex model handles this naturally; a RocksDB transaction model would need care not to Rollback on a WRONGTYPE.

## Open questions

- Actual per-EXEC overhead of WriteBatch vs OptimisticTransactionDB vs TransactionDB on macOS Apple Silicon is unmeasured; the only published first-party data is x86 from 2016 and omits the optimistic column. The db_bench randomtransaction recipe above needs to be run once RocksDB is installed.
- Whether the chosen Go or Rust binding exposes what this design needs: WriteBatchWithIndex with GetFromBatchAndDB and NewIteratorWithBase, OptimisticTransactionDB::Open with OptimisticTransactionDBOptions, and TransactionDBWriteOptimizations. Not checked in this pass; it may decide the language.
- Behaviour of the same shared_mutex pattern on Linux (libstdc++ over pthread_rwlock, whose default preference differs from libc++). Relevant only if NilDB keeps any global guard and targets Linux later.
- Kvrocks's raw-key WATCH table implies cross-namespace false aborts; inferred from WatchKey/updateWatchedKeysFromRange, not demonstrated with a test.
- How Dragonfly's SCAN/long reads interact with Lock-ahead EXEC (whether iteration holds shard locks) was not traced; only the MULTI modes and WATCH path were read.
- Whether Kvrocks issue #2554 has produced a design or PR since the 2024-09 comment; the issue was still open with no linked PR when fetched.
- Redis's remaining edge case from #9194 ('key already expired when WATCH ran') is now covered by the wk->expired flag in unstable; the exact release that closed it was not pinned down.

### 4. In Kvrocks, lazy expiry is not a modification for WATCH purposes, so Kvrocks does not implement Redis 6.0.9+ semantics. An expired key is detected at read time by Metadata::Expired() and surfaced as rocksdb::Status::NotFound(kErrMsgKeyExpired) with no write; physical removal happens only in the compaction filter. Because watched-key updates are driven solely by write-flagged commands, a watched key that expires between WATCH and EXEC never sets watched_keys_modified and EXEC proceeds.

### 11. With Kvrocks's design, a multi-second analytical command holding a RocksDB snapshot blocks EXEC for its whole duration, and on macOS (libc++) a waiting EXEC also blocks every new command on every worker until that scan finishes, because libc++'s shared_mutex is writer-preferring. The RocksDB snapshot itself never blocks writers; the stall is entirely the server-level rwlock.

Kvrocks: the shared_lock is held across ExecuteCommand (redis_connection.cc 555-720), so a long SCAN/aggregation holds it for seconds. libc++ src/shared_mutex.cpp 23-30: lock() 'while (__state_ & __write_entered_) __gate1_.wait(lk); __state_ |= __write_entered_; while (__state_ & __n_readers_) __gate2_.wait(lk);' and 51-54: lock_shared() 'while ((__state_ & __write_entered_) || (__state_ & __n_readers_) == __n_readers_) __gate1_.wait(lk);'. Thus once EXEC sets __write_entered_ while readers are active, all new lock_shared() callers wait. The head-of-line consequence is my inference from those two verified code paths; the same code on Linux libstdc++ uses pthread_rwlock and may schedule differently (unverified).

- Source: https://raw.githubusercontent.com/llvm/llvm-project/main/libcxx/src/shared_mutex.cpp
- Confidence: verified; design-critical: yes

### 18. ### 19. Dragonfly's design (docs/transaction.md, VLL-based) is the counter-example to stop-the-world EXEC: a MULTI/EXEC block runs as one multi-transaction in one of three modes: Global (shard-level lock on all shards, needed for FLUSHDB/MOVE and Lua with undeclared keys, 'Blocks all concurrent transactions across all shards, so it should be avoided'), Lock-ahead (pre-lock all declared keys, run commands as consecutive hops, other keys proceed concurrently), or Non-atomic. Command squashing groups the block's single-shard commands per shard and runs them in one parallel hop. Uncontended single-shard commands execute inline during scheduling without a TxId or queue insertion.

docs/transaction.md sections 'Multi-op Transactions (MULTI/EXEC, Lua)', 'Multi modes' (Global / Lock-ahead / Non-atomic with the quoted text), 'Command Squashing' (six-command example partitioned across three shards, 'Per-shard order is preserved'), and 'Scheduling a Transaction' ('the majority of transactions never allocate a TxId'; intent locks with SHARED/EXCLUSIVE counters; OUT_OF_ORDER execution when uncontended). ### 20. Dragonfly implements Redis 6.0.15+ WATCH-over-expiry semantics with a pull check at EXEC rather than relying on expiry deletion to fire a hook: each shard's DbSlice keeps per-DB watched_keys -> vector<atomic_bool*>; PostUpdate() (the write hook) sets each connection's watched_dirty and drops the entry; InvalidateDbWatches() marks all on flush. Exec() returns a null array if watched_dirty is set, then (after StartMulti has locked the keys) runs CheckWatchedKeyExpiry: an EXISTS hop over all watched keys whose count must equal watched_existed captured at WATCH time, plus the dirty flag; a mismatch means a watched key expired and EXEC returns null. WATCH and EXEC on different DBs is rejected.
