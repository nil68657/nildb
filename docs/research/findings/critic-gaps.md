# Critic verdict and research gaps

Exported on 2026-09-27 from the critique step of Claude Code run `wf_1b4f4c38-bbf` (agent `acda3ce2dde1cca7d`). The gap-fill agents for gaps 1, 2, 5, 6, 7 and 8 stopped at the Claude session limit twice and returned nothing.

## Verdict

The corpus is broad and, on most single topics, well sourced: prior-art key encodings (Kvrocks, Pika, Titan, Tidis), the Redis wire surface and error strings, RocksDB APIs with binding coverage, S2 and MongoDB 2dsphere internals, and BSON/document semantics are all traced to primary sources. It is not yet a design input, for four reasons. First, the seven sections disagree on the language (geo, toolchain and document sections say Go; HTAP and RocksDB sections say Rust) and nobody ran the experiments that decide it; the repo already holds a passing grocksdb v1.11.1 smoke test (bin/rocksmoke, exercised here: multi-CF batch, merge, compaction filter, snapshot, checkpoint) linked against Homebrew librocksdb 11.8.1 on this arm64 Mac, which closes one open question the corpus still lists but does not settle the rest. Second, the HTAP half rests on a columnar column-family layout the corpus invented without a precedent (Rockset's converged index and Kvrocks' JSON type were never examined), and the transaction model, SCAN cursor, index GC on expiry and aggregation memory bounds are all left as open questions rather than answered. Third, licensing is never consolidated even though the corpus cites Redis unstable (tri-licensed since 8.0), MongoDB server (SSPL), CockroachDB pkg/geo (CockroachDB Software License) and mongodb/specifications (CC BY-NC-SA 3.0) as templates to port from. Fourth, macOS durability is absent: Homebrew's librocksdb is built with HAVE_FULLFSYNC while rust-rocksdb's build.rs never defines it for darwin, so the two candidate toolchains give different crash guarantees and different sync-write ceilings, and no benchmark baseline exists for either. With the eight gaps below filled, an engineer can write the design; today they would make the four largest decisions (language, storage layout, transaction mode, license posture) on judgement rather than evidence.

## Gaps

### Gap 1: not researched (session limit)

Which single language stack can deliver all four hard requirements (spherical polygon $geoWithin/$geoIntersects, Redis MULTI/EXEC with read-your-writes, an embedded aggregation engine, and sub-10-microsecond point ops) without hand-porting a major library? Specifically: (a) does any Rust crate bind Google's C++ s2geometry (S2Polygon, S2RegionCoverer, S2ClosestEdgeQuery) via cxx/bindgen with a build that works on macOS arm64, and is the rust-s2 tracker actively porting Loop/Polygon/RegionCoverer; (b) golang/geo's polygon.go TODO block (around line 1205) lists DistanceToPoint, DistanceToBoundary, Project, InitToIntersection/Union/Diff, IsNormalized as missing: which of these do $geoNear-to-perimeter and hole handling need; (c) what is the measured cgo overhead per grocksdb Get/Put/Iterator.Next on Apple Silicon versus rust-rocksdb; (d) datafusion-go only offers RegisterArrowReader (copies batches into Rust) and RegisterFFITableProvider (a Rust-built provider), so is a materialise-then-query flow acceptable for the Go path or does DataFusion require Rust to be lazy?

Every downstream design (WBWI vs OptimisticTransactionDB for EXEC, compaction-filter callbacks, geo predicates, analytics engine) depends on this choice, and the repo has already started in Go (go.mod pins grocksdb v1.11.1, redcon, mongo-driver v2, golang/geo) on the strength of one smoke test.

### Gap 2: not researched (session limit)

How do RocksDB-backed systems that already serve both point ops and analytics lay out documents and per-field columns as keys, and what write amplification do they pay? Read Rockset's converged index (row index R.<docid>, column index C.<field>.<docid>, inverted index S.<field>.<value>.<docid>, all in RocksDB; 'stores each document twice'), Kvrocks' JSON type (one blob per key: flags|expire|format|payload in the metadata CF, indexed by KQIR in the search CF) and YugabyteDB DocDB's subdocument key flattening; then settle whether NilDB's analytical CF holds every field (Rockset, TiFlash) or only declared fields (Kvrocks FT.CREATE, RediSearch), how index and column entries are removed when a Redis key expires lazily or a doc TTL fires (Kvrocks Search's behaviour on expired hashes was never checked), and how $group/SORTBY memory is bounded (spill CF, hard limit, or RediSearch-style cursor).

Why it matters: The corpus's proposed 'collection|field|primary key' columnar CF has no source and no measured cost; TiFlash's 3.4x write amplification is the only number quoted and it is for a different engine. Without a precedent the HTAP claim is a guess, and expiry-driven index garbage is the failure mode Luo & Carey warn about.

### Gap 3: answered in [08-gap-transactions-and-watch.md](08-gap-transactions-and-watch.md)

What concrete transaction and concurrency model will NilDB run, and how does each candidate behave under WATCH, lazy expiry and long analytical snapshots? Trace Kvrocks' WATCH on RocksDB (server-side watched-key table, which write paths touch it, FLUSHDB/FLUSHALL handling, whether lazy expiry counts as a modification as Redis 6.0.9 requires per redis/redis#7920 and #9068), measure a plain WriteBatch versus one OptimisticTransactionDB transaction per MULTI versus pessimistic TransactionDB (which also locks non-transactional writes unless skip_concurrency_control), and determine how an EXEC exclusivity guard (Kvrocks WorkExclusivityGuard stops all workers) interacts with a multi-second aggregation holding a snapshot.

### Gap 4: answered in [09-gap-scan-cursors-keys-dbsize.md](09-gap-scan-cursors-keys-dbsize.md)

How should NilDB implement Redis SCAN cursors, KEYS and DBSIZE over RocksDB so that Redis's guarantees hold? Kvrocks already solved this: kvrocks.conf 'redis-cursor-compatible yes' (default since v2.5.0, PR #1489) maps an unsigned 64-bit cursor to a stored last key, otherwise the cursor is the key itself. Read the cursor dictionary implementation (size cap, eviction, behaviour after restart, per-namespace handling), how expired-but-not-compacted keys are skipped, the cost of the TYPE filter over the metadata CF, and how DBSIZE is served (Kvrocks' asynchronous 'DBSIZE SCAN' versus rocksdb.estimate-num-keys accuracy under tombstones).

Why it matters: The corpus proposes 'a hash or opaque offset' for the cursor without a design, while the Redis contract (full iteration returns every stable key, cursor is a u64) and redis-cli --scan/--bigkeys depend on it. DBSIZE cost is a documented Kvrocks deviation NilDB must consciously copy or avoid.

### Gap 5: not researched (session limit)

What durability does each toolchain actually give on macOS, and what throughput baseline should NilDB design against? Verified here: Homebrew's librocksdb 11.8.1 contains the 'while fcntl(F_FULLFSYNC)' strings, so it was built with HAVE_FULLFSYNC (RocksDB CMakeLists line 606 sets it when F_FULLFSYNC exists); rust-rocksdb's librocksdb-sys build.rs defines only OS_MACOSX, ROCKSDB_PLATFORM_POSIX and ROCKSDB_LIB_IO_POSIX for darwin and never HAVE_FULLFSYNC, so the bundled Rust build falls back to fdatasync (io_posix.cc lines 1607-1636). Measure F_FULLFSYNC cost on this Mac (reports put it near 2.5 ms per call versus about 58 microseconds for fsync), decide what 'appendfsync always/everysec' mean under each, and gather baselines: db_bench on Apple Silicon, Kvrocks' published redis-benchmark numbers, Redis/Valkey on the same Mac, plus a named HTAP acceptance workload (CH-benCHmark subset or a Redis-plus-aggregation mix).

Why it matters: The corpus's durability policy assumes WriteOptions.sync=true means power-loss safety; on macOS that is only true with F_FULLFSYNC, and only one of the two candidate builds has it. No section gives a single throughput or latency number for the target machine, so the HTAP isolation target (10 percent TP degradation, borrowed from TiDB) has nothing to be measured against.

Search hints: rocksdb env/io_posix.cc HAVE_FULLFSYNC fdatasync; rust-rocksdb librocksdb-sys build.rs HAVE_FULLFSYNC issue; rocksdb issue 5954 fsync macos F_FULLFSYNC; rocksdb pull 9356 F_FULLFSYNC performance; F_BARRIERFSYNC vs F_FULLFSYNC latency APFS; rocksdb db_bench Apple M1 M2 M3 results; kvrocks performance benchmark redis-benchmark QPS; valkey redis-benchmark macOS arm64; rocksdb use_direct_io macOS F_NOCACHE unsupported; CH-benCHmark single node redis
